# 64-bit migration research

## Recommendation

Keep the working i386 engine as the default and as the reference while building a native 64-bit path in this repository. Automate an inventory and migrate connected groups of existing rewrites, rather than extracting unrelated leaf functions one at a time. A real native game must replace fixed-address dispatch, guest-layout pointers, x86 ABI assumptions and x87-dependent behavior; compiling with `-m64` does not do this.

The standalone maps the player's PE32 image at `0x400000`, installs rewrites and traps unreplaced functions (`hook/standalone.h`). It still depends on the image's data and addresses. `PortFn` stores untyped function pointers (`hook/port.h`); `ui_types.h` dereferences guest pointer slots and invokes guest vtables; many original-layout classes contain native pointers and have exact 32-bit layout assertions. `hook/x87.h` documents the physics precision requirements. A text search finds about 10,150 `PORT_FN`-style occurrences in 98 C++ files, including generated registrations, duplicates and comments: this is a scale indicator, not a count of independent functions or remaining work.

## Efficient path

1. Preserve a **native i386 oracle** with original assets: capture session and race replays, per-tick state, menu frames, and multiplayer behavior. QEMU is useful for portable smoke tests but its SEH fault results differ here; it is not the physics or exception oracle.
2. Extend the existing `tools/gen_port_tables.py` and `tools/gen_standalone.py` analysis with a read-only machine-readable inventory: registrations, file-local definitions, direct and indirect function references, globals, serialized fields, vtables, and inline assembly. Classify unknowns explicitly; track dependencies and connected groups. Existing generated inventories are starting evidence, not proof that call signatures are correct.
3. Prototype Clang AST tooling on one tractable translation unit using actual build flags and a compilation database. Generate or check typed declarations and direct native calls only where the signature and ownership are established. Fail the native build for unresolved guest calls; do not replace integer-to-function-pointer casts mechanically. Some GCC/MSVC x86 assembly and macros may prevent Clang from parsing particular files, so record coverage and retain a fallback. [Clang LibTooling](https://clang.llvm.org/docs/LibTooling.html) and [AST matchers](https://clang.llvm.org/docs/LibASTMatchers.html) provide the relevant APIs.
4. Separate 32-bit guest addresses and on-disk/network layouts from native objects. Translate guest data through bounded views and stable IDs; do not store 64-bit pointers in four-byte fields. Audit Windows LLP64 and Linux LP64 separately. Convert one connected startup/input/UI slice to typed native calls and real state, then exercise it through the actual game loop. A portable helper alone is not a game milestone.
5. Build canonical field-based cross-architecture traces. Raw object bytes and addresses differ; `hook/replay.cpp` currently filters pointer-looking words and is not by itself a proof of native equivalence. Compare inputs, events and semantic state, then use existing shadow, replay and session harnesses where applicable. ASan/UBSan supplement but do not replace parity tests.
6. Treat physics as its own gate. Use the checked-in `test/x87_parity_corpus.cpp` on native i386 and x86-64, then compare actual functions and races. Capture x87 control/status, MXCSR, NaNs, denormals, rounding and first divergence. GCC documents that SSE is the x86-64 default and that excess precision changes arithmetic ([x86 options](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html), [optimization options](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)). Windows x64 uses a different floating-point ABI and does not support MSVC x64 inline assembly ([x64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170), [MASM for x64](https://learn.microsoft.com/en-us/cpp/assembler/masm/masm-for-x64-ml64-exe?view=msvc-170)). A compiler flag alone is not a parity result.
7. Expand by dependency group, with Windows/Linux builds and real race, replay, save and multiplayer acceptance tests. Keep the i386 release intact until the native version passes those gates.

## Alternatives considered

- **32-bit engine on a 64-bit OS:** quickest compatibility route and current baseline; it is not a native 64-bit engine. [QEMU user mode](https://www.qemu.org/docs/master/user/main.html) can run foreign-architecture user programs, but results in this environment do not establish native parity.
- **64-bit frontend and 32-bit worker:** can isolate simulation temporarily, but requires a second process, cross-bitness IPC and latency analysis. It conflicts with the single-executable, fully native goal; 64-bit Windows cannot load a 32-bit DLL into a 64-bit process ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/winprog64/process-interoperability)).
- **Static binary translation:** [M-HT/SR](https://github.com/M-HT/SR) reports translating some Windows x86 games to x64; [pcrecomp](https://github.com/sp00nznet/pcrecomp) provides x86 lifters and differential-testing tools. These are candidates for a bounded experiment, not verified Viper solutions: this fork already has rewrites and a purpose-built runtime, and binary lifting would need independent validation of hooks, imports, x87, data, threading, and licenses for generated output. Do not replace or merge the engine based on a tool's advertised coverage.

No approach above has yet produced a native 64-bit Viper Racing executable. The first acceptance milestone is an actual native startup-to-input/UI slice with typed dispatch and canonical cross-width tests, followed by a parity-tested race, not merely a successful `-m64` compilation.

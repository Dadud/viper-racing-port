# Mod compatibility

The inventory recognises loose `.car`, `.trk`, and `.tra` files case-insensitively. These are 0TSR containers with a directory and sequential member payloads. It checks directory and payload bounds, preload counts and boundaries, and chunk markers, recognises the documented `lockd*.tab` padding used by some community cars, and reports duplicate member names. For tracks it reports the member set observed in the toolkit's samples. For cars it checks the selected archive stem against `<name>.cf` and `<name>0.mod`, and checks the physics resource type, version and size. Missing members can come from shared archives; these checks are advisory and do not establish playability. No file is modified or extracted.

Format research: Herb Fargus's [vrmod archive parser](https://github.com/HerbFargus/viper-racing-modding/blob/main/vrmod/archive.py) and [track module](https://github.com/HerbFargus/viper-racing-modding/blob/main/vrmod/track.py) document the container, decoy padding, and observed track members. This implementation is independent; no toolkit code is bundled. The toolkit is MIT licensed. `.mod`, `.tex`, `.cf`, `.stp`, `.ili`, and `.ild` are resources inside containers; this inventory does not parse or validate their contents or resolve their references. ZIP/RAR discovery, installation, missing texture analysis, provenance, and automatic shared-resource dependency resolution are not implemented. A read-only API can inspect `.res` archives and resolve a named resource against a caller-supplied search order; it does not imply that the game will use that order.

The [community gallery](https://github.com/HerbFargus/viper-racing-gallery) generates its catalog and previews with vrmod and preserves attribution and source information. No gallery adapter or downloads are implemented. The [historical tools](https://github.com/HerbFargus/viper-racing-legacy-modding-tools) repository records the provenance of several original and community tools; its contents have not been bundled.

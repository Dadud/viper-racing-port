# Architecture notes

The standalone loader is `loader/viperport_linux.cpp` on Linux and `loader/` on Windows. `hook/standalone.cpp` and `hook/viperport.cpp` install the engine; the port uses fixed original addresses and 32-bit layouts. `hook/krn_res.cpp` manages resource archives, `hook/wld_cars.cpp` loads the race world and cars, `hook/root_race.cpp` builds the race selection lists, and `hook/menu_view.cpp` implements the viewers. `hook/gl_core.cpp` is the OpenGL renderer. Physics and AI are in `hook/phys_*.cpp` and have replay and shadow checks described in README.

`content_registry` and `content_catalog` are portable C++17 APIs used by the game adapter in `hook/content_game.cpp`. A scan recursively indexes loose car and track bundles, verifies their container structure and recognized MINF model layouts and signed vertex-index limits, exposes resource descriptors and advisory dependencies for cars and tracks, and provides case-insensitive name search. `scan_roots` combines legacy game-folder and managed-library roots, deduplicates overlapping paths (case-insensitively on Windows), and compares bytes before marking duplicate packages. `Catalog` filters by kind, search text, author, version, description, and favorites; persists favorites; and returns owned browser rows so a refresh cannot invalidate UI display data. Its game paths place managed packages and favorites below the existing `Config` directory. Selection re-reads both archives, refuses a file changed since the scan, checks the car physics resource, and resolves observed dependencies against the engine's currently loaded shared archives. Setup staging verifies stable IDs and exact archive paths. The single-race UI in `hook/menu_race.cpp` adds searchable car and track dialogs, favorites, metadata and validation details; its list capacity follows the result count rather than a fixed entry cap, within the legacy UI's 32-bit allocation limits. Selected set names must fit the legacy 32-byte car and track name fields, including the terminating NUL, before setup writes them into the race state. `hook/krn_res.cpp` opens the exact selected archive path before the engine's normal lookup. If a different same-name set has higher priority, it loads the selected file again at the front; explicit `set/resource` requests for the selected set are then restricted to that exact loaded path, so lookup cannot fall through to a lower same-name package. Unqualified resource lookup and other set names retain the engine's search order. A selected file that cannot be opened aborts the load rather than substituting another package. With no library selection, resource lookup follows the existing path. `RaceSelectionContext` owns the temporary selection and is cleared on cancellation, setup/load completion, and race unload. `valid` means the archive and recognized model layouts are structurally valid, not a promise that a race will load; asset-backed race smoke tests have entered a race on v1.0 and community v1.2.6, while runtime validation of v1.1 and community v1.2.4/.5 remains outstanding. Optional adjacent `<archive filename>.json` files attach author, version, and description metadata without changing archive identity. IDs contain the content kind and SHA-256 of the entire archive and remain stable when a file is moved. An edited or repacked archive has a different identity. Metadata parse failures are reported separately. `install_archive` and `uninstall_archive` remain portable API operations; the in-game library milestone does not add install controls or archive extraction. `search` still returns pointers owned by a `Registry`; do not retain them across registry modification or destruction. `content_preferences` stores favorite content IDs in a versioned file, preserving IDs for absent content; the caller selects the file location and handles errors. `inspect_shared` and `resolve_resource` permit explicit, read-only inspection of shared archives; the caller supplies their precedence, and invalid archives or duplicate names produce indeterminate or ambiguous results.

Legacy full-screen dialogs whose item geometry fits the original 640x480 canvas scale uniformly by the smaller screen axis and stay centered, preserving the original layout proportions on widescreen displays. `UIDoMenu` applies the same centered canvas and font/stamp scaling to the main menu title and buttons; screens wider than the canvas remain centered even when their height limits scaling. The content browser has its own responsive window (up to 2200x1280); its section spacing, search field, and footer follow the effective font scale, which is capped to fit that window. On short stacked layouts, the results list preserves a visible row where space allows and no longer forces a 64-pixel minimum that covered the details heading. The native x64 selector centers its content column on ultrawide displays and shows package provenance beneath each result. Its selection model opens the selected car and track with `ArchiveReader`, then `native_resource::Store` routes named reads to the selected archive first and the active shared archive order second, with a caller-supplied byte limit. The SDL car browser separately opens the selected car by stable ID, parses its `<car>0.mod` MINF resource, and renders the resulting mesh as a color-coded wireframe in the details card; its 16 MiB read and 250,000-triangle limits bound allocations. The decoded model is reused while the same ID remains selected. The track browser parses the selected `track.bpp` into checked host-owned triangles and 2D splitter indices, rejects cycles and invalid references, and exposes point-height plus segment-versus-triangle queries following the observed BPP traversal order. Segment queries select legacy x87 24-bit physics or 53-bit UI arithmetic explicitly; the original-executable corpus matches exactly on x86 and x64 for 38,434 finite queries across eight stock tracks. The full collision system remains unported. The details card draws the mesh as a surface-colored overhead map. Both preview meshes cap rendering at 250,000 triangles. These handles remain owned until selection cancellation or replacement. The portable content tests sweep common viewport sizes through 4K and include a 32:9 case, covering the 4K font cap and constrained-height row geometry; this verifies layout arithmetic, not an in-game visual pass.

The catalog and recognized MINF checks pass their x86 and x64 test builds against the local v1.0 and community 1.2.4, 1.2.5, and 1.2.6 `Data` folders. Each folder's 13 loose archives and 50 model resources were accepted. The x86 `world_krn_res` harness read each local community `Data` tree (26 resource sets and 2 file resources; 11,510 checks with zero differences per tree) and passed its synthetic selected car and track archive test against each tree. The test confirms each selected payload is returned, the lower-priority same-name payload is hidden, and a missing selected archive fails closed. These checks exercise the shared resource resolver and local archive contents; they do not prove that each build's in-game setup adapter worked or that every package is playable. In-game UI and race validation for v1.1 and community 1.2.4/.5 remains open.

`RaceSelectionContext` retains the caller-supplied shared archive order across resource resolution and load-time revalidation. An adapter can replace that snapshot if the engine resource list changes; failed revalidation clears both the selection and the shared snapshot.

`RaceBegin` still builds the legacy car list and reads `tracks.tab` for the stock setup; the library is a separate single-race picker layered before load. The 16 entries in `World::CarList` are participants in one race, not a limit on the content inventory. Saves, replays, career data, and network sessions still use legacy names or slots, so the temporary stable-ID selection is intentionally cleared before those formats can observe it. A native port must define any persistent identity translation before changing those interfaces.

## 64-bit migration

The current game is an i386 process, not merely a 32-bit build setting. The Linux loader maps the v1.0 PE at `0x400000` and enters through its 32-bit entry address after installing rewritten functions; the standalone normally traps unreplaced code rather than routinely running original functions. Rewrites still call fixed x86 addresses and depend on 32-bit calling conventions, embedded pointers, and exact original object layouts. A 64-bit process cannot safely call these x86 entry points or widen those structures. The existing executable and replay checks remain the compatibility baseline.

The Linux loader uses host-width-independent SHA-256 and PE32 inspection code to verify and inspect the original executable. PE inspection and image copying use explicit offsets and validate headers, sections, and image bounds before the existing i386 execution path runs; it does not execute x86 code in a 64-bit process. `legacy::MemoryView` is a host-width-independent, bounds-checked view of 32-bit guest addresses over a host buffer. It is a tested migration building block, not yet used by the engine or a replacement loader. It demonstrates translating an address without truncating a host pointer and explicitly checks the 4 GiB boundary. `tools/test_portable.sh` builds its tests and the independent content-library tests for the host architecture.

A native 64-bit engine requires replacing fixed-address calls and original globals with native interfaces, separating serialized/guest 32-bit layouts from host objects, and eliminating or emulating remaining original x86 code and ABI assumptions. The UI dispatch helpers dereference 32-bit pointer slots and call fixed addresses as function pointers; native code needs typed dispatch and separate host objects rather than wider pointers in guest layouts. The exception layer also assumes x86 registers and FS, while physics depends on x87 precision. Migrate subsystems behind explicit interfaces and compare physics, menus, replays, saves and networking against the 32-bit baseline before considering the 64-bit game usable. The existing `w32_path` implementation is exercised directly by portable 64-bit and i386 tests, including file offsets above 4 GiB; this does not establish that its callers are 64-bit safe. Windows and Linux require separate ABI and platform verification.

The network CRC16 loop now accepts its lookup table as an explicit typed dependency; the i386 adapter still supplies the guest table. The game's Base64 quad and buffer transforms similarly accept typed callbacks, while their i386 adapters retain the existing guest calls and legacy buffer-size behavior. The separate native ASCII Base64 lookup rejects high bytes instead of reproducing the legacy decoder's out-of-bounds table access. The POSIX time stand-ins use the native calling convention on 64-bit hosts, while retaining stdcall on i386. These are subsystem-level steps, not a guest-to-native dispatch layer.

The CRT `strncmp` rewrite shares a host-width-independent implementation with native tests, while its legacy wrapper remains in place. Winsock host-entry serialization takes an explicit 32-bit guest base separate from its native buffer; the existing adapter only accepts host pointers representable in guest space. This is not a complete native Winsock ABI. A preliminary QEMU i386 versus x86-64 x87 probe produced different results, but emulation and ABI effects have not been isolated: native i386 differential testing remains necessary before moving physics.

Additional native-width pilots expose keyboard scan state, reliable packet sequence arithmetic, and CRT memory movement through typed functions while preserving their i386 adapters. The heap stand-in uses opaque 32-bit handles for native 64-bit callers rather than truncating host pointers; its i386 address handles remain. Heap allocations still return host pointers and do not yet provide a guest-memory bridge.

The UI string-list add, get, and delete operations now live in a host-width-independent core. `ui_core::OwnedStringList` owns native buffers with stable entry addresses, and `test/ui_string_list_core_test.cpp` exercises that host implementation. The existing UI rewrite passes fields from its original `UIStringList` ABI object into the same operations; it still uses the original allocator and ABI layout. This is a tested native data component, not native UI startup or rendering.

`test/x87_parity_corpus.cpp` outputs deterministic per-case float bits and x87/SSE status across precision and rounding modes. It is a diagnostic, not a game-physics test. Compare it with a native i386 run; QEMU alone is not an oracle.

`tools/64bit_inventory.py` emits a read-only JSON inventory of literal `PORT_FN` registrations and guest-range address occurrences in `hook/*.cpp`. It is lexical: it does not evaluate preprocessor branches, resolve aliases or signatures, or establish call edges. Current counts are occurrences, not unique functions or confirmed dependencies. Run `python3 tools/64bit_inventory.py --output /tmp/viper-64bit-inventory.json` to regenerate it. `bash tools/build_linux.sh compile-db` emits the compiler database from the same expanded flags as the i386 build; it requires the Linux build dependencies, including `sdl2-config`. `VP_COMPILE_COMMANDS=1` opts into emitting it during a build. Neither tool changes the default engine build.
